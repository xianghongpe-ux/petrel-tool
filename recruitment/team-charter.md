# 核心团队工作章程

## 🌐 章程前言

本章程定义了海燕党（PETREL AI PARTY）核心贡献者团队的
**组织结构、决策机制、会议制度和工作纪律**。

所有核心贡献者必须签署本章程，认同并遵守其中各项条款。

> **"不是因为代码能运行就提交，而是因为提交的每行代码都能被社区信任。"**

---

## 📖 第一章：总则

### 第 1 条 团队使命

核心贡献者团队（Core Contributors Team）是海燕党的技术执行核心，
负责：
1. 协议设计与实现
2. 代码质量管控
3. 社区技术支持
4. 生态建设与对外合作

### 第 2 条 基本原则

1. **公开透明** —— 全部决策过程公开，全部会议记录可查
2. **代码即法律** —— 代码质量高于一切，签名提交是底线
3. **贡献驱动** —— 影响力来源于实际贡献，非头衔
4. **去中心化治理** —— 不依赖单一个人或机构

---

## 👥 第二章：组织结构

### 第 3 条 角色体系

| 角色 | 权限 | 任期 |
|------|------|------|
| 核心贡献者 | 代码写入、决策投票 | 永久（自愿退出除外） |
| 维护者（Maintainer） | PR 审核、模块维护 | 12 个月，可连任 |
| 协议架构师 | 架构决策否决权 | 24 个月，可连任 |
| 社区经理 | 社区运营、对外联络 | 12 个月，可连任 |

### 第 4 条 角色晋升

- **核心贡献者 → 维护者**：持续 6 个月高质量贡献 + 现有维护者投票 > 2/3
- **维护者 → 协议架构师**：持续 12 个月 + 架构贡献 + 全体投票 > 3/4
- 任何角色均可由本人随时申请退出

### 第 5 条 角色撤销

- 连续 3 个月无有效贡献（自动化系统自动标记）
- 严重违反行为准则（全体投票 > 2/3）
- 恶意提交或引入后门（立即撤销 + 社区公告）

---

## 🗳️ 第三章：决策机制

### 第 6 条 决策层级

| 决策类型 | 决策方式 | 生效条件 |
|----------|----------|----------|
| 日常技术决策 | PR Review | 至少 1 个 Maintainer Approve |
| 模块级变更 | RFC + PR Review | 至少 2 个 Maintainer Approve |
| 协议级变更 | PIP（Petrel Improvement Proposal） | 核心贡献者投票 > 3/4 |
| 治理规则修改 | 章程修订 | 核心贡献者投票 > 4/5 |

### 第 7 条 PIP 流程

1. **草案阶段**：创建 GitHub Issue，标记 `pip-draft`
2. **讨论阶段**：至少 7 天公开讨论
3. **投票阶段**：核心贡献者投票，持续 7 天
4. **实施阶段**：通过后 30 天内提交参考实现
5. **激活阶段**：参考实现合并后，PIP 正式生效

### 第 8 条 投票规则

- 每个核心贡献者 1 票
- 投票通过率按上述条款执行
- 弃权计入总票数（等同于反对）
- 投票结果在公共看板公示

---

## 📅 第四章：会议制度

### 第 9 条 双周公开例会

**频率**：每两周一次，北京时间周五 20:00

**议程**：
```
1. 轮值主持开场（5 分钟）
2. 各工作组进度报告（15 分钟）
3. 当前 PIP 讨论（20 分钟）
4. 社区提问环节（15 分钟）
5. 自由讨论（15 分钟）
```

**记录要求**：
- 全程录屏 + AI 自动速记
- 48 小时内生成会议纪要，发布至公共看板
- 决议项标注负责人与 DDL

### 第 10 条 临时紧急会议

在以下情况下可召开：
- 发现高危安全漏洞
- 网络升级紧急决策
- 治理危机处理

临时会议 24 小时内召开，紧急决策有效期 7 天。

## 📋 第五章：工作看板

### 第 11 条 公开路线图看板

海燕党使用 GitHub Projects 管理全部工作任务：

**看板地址**：`https://github.com/orgs/PetrelAIParty/projects/1`

**看板列配置**：
```
📋 Backlog → 🔜 Next → 🔧 In Progress → 👀 Review → ✅ Done
```

### 第 12 条 看板管理规范

1. 所有工作任务必须在看板上体现
2. Issue 必须包含：描述、验收标准、负责人、预估工时
3. 每个 Sprint 周期为 2 周（与例会节奏对齐）
4. 严禁未经看板追踪的"暗箱任务"

### 第 13 条 里程碑管理

里程碑以 `v{major}.{minor}.{epoch}` 格式命名：

```
v1.0.0  — 核心协议主网启动
v1.1.0  — DAO 治理模块上线
v2.0.0  — L2 扩容方案发布
v3.0.0  — 去中心化治理完全自治
```

每个里程碑必须包含：
- 功能清单（链接至 Issue）
- 验收标准
- 目标时间线
- 风险评估

## 📝 第六章：工作纪律

### 第 14 条 代码提交规范

1. **所有提交必须 GPG 签名**（参见 `commit-signing.md`）
2. **Commit Message 必须符合 Conventional Commits 规范**
3. **所有 PR 必须通过 CI 全部检查才能合入**
4. **任何删除创世铭文的 PR 自动拒绝**（由 CI `genesis-guard.py` 强制执行）

### 第 15 条 沟通纪律

1. 公开讨论使用 GitHub Issues，内部讨论使用 Matrix
2. 禁止在未经授权的渠道讨论安全漏洞
3. 对外发言需注明"个人观点，不代表海燕党官方立场"
4. 讨论应保持专业、尊重、建设性

### 第 16 条 冲突处理

1. 技术分歧通过 RFC/PIP 流程解决
2. 人际冲突由社区经理协调
3. 严重争议提交全体核心贡献者投票
4. 涉及违法/违规行为立即上报
